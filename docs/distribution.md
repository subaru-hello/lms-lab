# 配信設計 — 記事が本体、Shortsが入口

## 判断の根拠

OctoByteの実測では Shorts が総再生の98.5%を占め、本編はほぼ見られていない。
Short→本編の遷移は実数5回（0.025%）で、唯一の非循環な入口は検索（14.4%）。
したがって:

- **開発過程を残す本体は Zenn の記事と公開リポジトリのタグ**（検索で拾われ、後から読める）
- **OctoByte には Shorts だけ載せる**（1本=1つの破れ方。既存のShortsシリーズの機械をそのまま使う）
- **本編は作らない**。作るとしても、シリーズ完走後に「全部つなげた版」を1本だけ
- **X は各記事の破れる瞬間を30秒の画面録画で投げる導線**。note は完走後のまとめと有料化の受け皿

「正しい実装の解説」から始めない。AIが出せるのはそこなので、そこは記事の後半に置く。

## OctoByte Shorts（全12〜15本）

- 必須5本: 上の破れ方5つ。各30〜50秒、山場は「破れている画面」そのもの
- 追加候補: HLSの中身をcatで見せる / 署名の中身を分解 / 冪等キーの1行 / R2とStreamの費用比較
- タイトルは【カテゴリ】先頭固定。シリーズ内で同じカテゴリに揃える（例: 【壊れるシステム】）
- 声・BGM・尺の規約は既存のShortsシリーズに準拠

## 順番

記事 → 同日にX（記事の破れる瞬間の画面録画つき） → 数日内にShort。
記事を書く前にShortを作らない。記事が一次資料で、Shortはその抜粋。
