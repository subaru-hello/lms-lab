# 破れ方 #1 — 公開バケットに置いた動画は、誰でも見られる

対応タグ: `l41-broken` / 直すのは段5。

## 何をしたか

R2 のバケット `lms-lab-videos` に動画を1本置き、`r2.dev` の公開アクセスを有効にした。
アプリ側は公開URLをそのまま `<video src>` に渡している(`src/lib/storage.ts`)。

## 実際の挙動（2026-09-03 実測）

Cookie も Authorization ヘッダも付けずに叩いた結果。

```
$ curl -o /dev/null -w "%{http_code} %{size_download}" \
    https://pub-920849089a154b709a891b123d69a3e0.r2.dev/lessons/2/source.mp4
200 413004

$ curl -o /dev/null -H "Range: bytes=0-1023" -w "%{http_code} %{size_download}" \
    https://pub-920849089a154b709a891b123d69a3e0.r2.dev/lessons/2/source.mp4
206 1024
```

- 匿名で 200、ファイル全体 413,004 バイトが落ちてくる
- Range リクエストに 206 を返す = 動画プレイヤーからそのまま流せる

ログインしていない、買っていない、そもそもアプリを開いてすらいない状態で再生できる。
アプリ側でどれだけ権利チェックを書いても、このURLが配られた時点で意味がない。

## なぜこうなるか

権利チェックが「アプリの画面を開く経路」にしか無く、
「動画の実体を取りに行く経路」には無いため。
Lesson テーブルに動画URLを持たせていないのはこの伏線で、
URLを列に置くと、それを返す全ての経路に同じ穴が開く。

## 直し方

タグ `l53-complete`。差分は `git diff l41-broken l53-complete`。

R2 の前に Worker を1枚置き、そこを唯一の関門にした。
Worker は「署名が正しいか」しか見ない。「この人が見てよいか」はアプリ側が判断し、
判断が済んでから署名を発行する。役割を分けているのは、動画1本を配る経路に
DBを覗きに行かせないため。

`node --env-file=.env --import tsx scripts/verify-signing.ts` の実行結果（2026-09-03）:

```
PASS  署名なし（段4.1で通っていた形）   403  reason=missing_params
PASS  正しい署名                        200  413,004 bytes
PASS  正しい署名 + Range                206  1,024 bytes
PASS  期限切れ                          403  reason=expired
PASS  鍵が違う                          403  reason=bad_signature
PASS  別パスの署名を使い回す            403  reason=bad_signature
PASS  存在しないキー                    404
```

### 実装中に踏んだバグ

`env.VIDEOS.get(key, { range: request.headers })` を無条件に渡すと、
Range ヘッダが無いリクエストにも R2 が range を埋めて返してくる。
そのまま分岐すると、Range を要求していない相手に 206 を返すことになる。
検証スクリプトの「正しい署名」ケースが 200 ではなく 206 になって気づいた。
ヘッダの有無で明示的に分けて直した。
